Architecture

구조 설계

구조

행동트리 기반 AI 구조

설계 의도

몬스터마다 행동을 따로 구현하면 같은 행동이 중복되고, 조건이 늘수록 어떤 상황에서 무엇이 실행되는지 추적하기 어렵습니다.

구성

조건/흐름/행동/데이터를 노드 종류로 나눠 엔진 컴포넌트로 만들었습니다. 노드는 실행 전 조건 검사와 실행 후 재검사를 나눠 처리하고, 진행 중인 노드를 트리가 기억해 다음 프레임에 이어갑니다. Decorator는 13종을 구현했습니다.

팀 접점

트리는 ImGui 에디터로 편집해 JSON으로 저장하므로, 몬스터 행동을 바꿀 때 코드를 다시 빌드하지 않습니다. 몬스터 속성은 구조체로 주입하고 이벤트는 델리게이트로 넘겨 외부에서 붙이도록 했습니다.

Troubleshooting

문제 해결

이미지를 누르면 크게 볼 수 있습니다.

CASE 01

일정 안에 필요한 행동 패턴 수를 채우지 못하던 문제

문제

5인, 2개월 일정에서 몬스터 타입과 행동 패턴을 계속 늘려야 했는데, 남은 기간 안에 필요한 수를 채우기 어려웠습니다.

원인

행동트리는 행동 하나를 넣을 때 노드 클래스 작성, 에디터 배치, 블랙보드 키 정의가 모두 필요해 패턴 추가 속도가 일정을 따라가지 못했습니다.

선택

구조적 확장성과 남은 기간 중 후자를 우선했습니다. 이미 만든 행동트리는 유지하고, 이후 추가되는 몬스터는 FSM으로 구현하는 절충안을 택했습니다.

구현

상태를 열거형으로 정의하고 전이를 직접 기술하는 EasyFSM을 만들어, 몬스터별로 상속해 진입·전이·종료만 채우도록 했습니다.

검증

전환 이후의 주차별 패턴 추가 수를 기록해 목표 수량을 채웠는지 확인했습니다.

남은 한계

구조가 두 가지로 나뉘어 몬스터마다 코드를 읽는 방식이 달라졌습니다.

CASE 02

대량 사망 구간에서 프레임이 급격히 떨어지던 문제

23 → 58 FPS
문제

몬스터가 많은 상황에서 광역 무기로 다수가 한 번에 사망하면, 그 순간 프레임이 급격히 떨어졌습니다.

원인

다수 몬스터가 동시에 제거·재생성되면서 메모리 할당과 해제, 생성 비용이 한 프레임에 몰렸습니다.

선택

동시 사망 수를 제한하면 광역 무기의 의도를 해치고, 여러 프레임에 분산하면 연출이 늘어집니다. 비용을 미리 치르는 풀링을 택했습니다.

구현

로딩 시점에 몬스터를 미리 생성해 비활성 상태로 보관하고, 사망 시 파괴 대신 풀에 반환한 뒤 초기값을 대입해 지정 좌표로 재배치했습니다.

검증

같은 조건에서 프레임 시간을 전후 비교해, 반복 생성·삭제 비용이 줄고 사망 순간의 런타임 스파이크가 완화되는 것을 확인했습니다.

남은 한계

풀 크기를 고정값으로 잡아, 예상보다 많이 필요할 때는 대응하지 못합니다.

CASE 03

경로 이동과 루트 애니메이션이 서로 밀던 문제

문제

내비게이션으로 이동 경로가 정해져도 루트 애니메이션이 적용되어 이동값이 애니메이션에 종속되면서, 추적 동작이 어색해졌습니다.

원인

이동 방향은 경로가, 이동 거리는 애니메이션이 결정해, 두 값이 서로 다른 기준으로 움직이고 있었습니다.

선택

루트 애니메이션을 끄면 이동 속도감이 사라지므로, 두 값을 모두 쓰되 역할을 나누는 쪽을 택했습니다.

구현

애니메이션에서는 이동 거리만 가져오고, 방향은 경로의 다음 목적지 벡터에서 가져와 곱한 값으로 좌표를 갱신했습니다. 회전은 목적지 방향으로 서서히 보정했습니다.

검증

장애물을 우회해야 하는 구간에서 경로 이탈 없이 도착하는지, 이동 속도가 애니메이션과 어긋나지 않는지 반복 확인했습니다.

남은 한계

회전 보정 속도가 고정값이라 급격히 꺾이는 경로에서는 몬스터가 살짝 미끄러져 보입니다.

CASE 04

컷신 진행 중에도 몬스터가 등장하던 문제

문제

시간 기반 몬스터 리스폰이 연출 상태와 무관하게 동작해, 컷신 진행 중에도 스폰 조건이 충족되어 몬스터가 등장했습니다.

원인

시간과 스폰 조건을 객체마다 따로 관리해 기준이 흩어져 있었고, "스폰 금지"라는 상태를 한 곳에서 표현할 수단이 없었습니다.

선택

각 객체에 컷신 여부를 묻는 방식은 참조가 늘어나므로, 이벤트 전체가 참조하는 공유 기준을 하나 두는 쪽을 택했습니다.

구현

이벤트 진행용 공유 시간 기준을 두고, 그 값이 정해진 임계 이상일 때만 스폰을 허용하도록 조건을 통일했습니다. 이벤트 종료 시 동작은 타이머에 람다로 등록했습니다.

검증

컷신 구간을 반복 재생하며 의도치 않은 스폰이 발생하지 않는지 확인했습니다.

남은 한계

시간 임계값으로 판단하다 보니 컷신 길이가 바뀌면 값을 다시 맞춰야 합니다.

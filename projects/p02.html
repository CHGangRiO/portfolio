Architecture

구조 설계

구조

파츠로 분리된 모델을 하나의 캐릭터로

설계 의도

캐릭터가 얼굴, 머리, 의상, 무기 등 파츠 파일로 나뉘어 있고 일부 본이 중복되어, 파츠마다 애니메이션을 따로 돌리면 동작이 어긋납니다.

구성

본과 애니메이션은 CModel_Pos 하나가 갖고, 파츠 8종은 CModel_Draw로 메시와 머티리얼만 가집니다. 모델을 읽을 때 기존 본 목록을 넘겨 병합하고, 불필요한 본은 걸러냈습니다.

효과

본 1세트를 파츠 8종이 공유하므로 같은 애니메이션이 전체에 동일하게 적용되고, 파츠를 추가해도 애니메이션 처리를 다시 만들지 않습니다.

구조

계층형 상태 머신 기반 전투 제어

설계 의도

상태가 늘수록 상태 간 전이 조건이 급격히 늘어, 어떤 상태에서 어디로 갈 수 있는지 추적하기 어려웠습니다.

구성

계층 간 전이는 FSMContainer가, 계층 안의 상태 전이는 StateMachine이, 애니메이션 지정과 종료 판정은 BaseState가 맡도록 3단으로 나눴습니다.

효과

피격·사망처럼 어느 계층에서나 발생하는 전이를 Container에서 한 번만 정의하면 되고, 상태를 추가할 때 영향 범위가 그 계층 안으로 제한됩니다.

Troubleshooting

문제 해결

이미지를 누르면 크게 볼 수 있습니다.

CASE 01

모델 로딩에 실행마다 약 2분이 걸리던 문제

2분 → 20초
문제

Assimp로 원본 모델을 직접 로드할 때 실행마다 약 2분이 걸렸고, 모델이 복잡할수록 초기 로딩이 크게 늘었습니다.

원인

원본 파일 전체를 파싱해야 했고, 애니메이션/본/메시 데이터를 매 실행 초기화 단계에서 다시 처리하고 있었습니다.

선택

비동기 로딩은 체감만 개선하고 반복 테스트 비용은 그대로입니다. 준비 비용을 최초 1회로 옮기는 직렬화를 택했습니다.

구현

런타임에 필요한 메시/본/애니메이션만 추출해 별도 포맷으로 저장하고, 실행 시에는 역직렬화만 수행하도록 준비 단계와 실행 단계를 분리했습니다.

검증

동일 조건에서 반복 측정한 결과 로딩이 약 2분에서 20초 이하로 줄었고, 반복 테스트와 디버깅 주기가 짧아졌습니다.

남은 한계

원본 모델이 바뀌면 다시 직렬화해야 하는데, 변경 감지와 자동 갱신까지는 넣지 못해 수동으로 처리했습니다.

CASE 02

애니메이션 이동과 실제 월드 위치가 어긋나던 문제

문제

대쉬처럼 이동이 포함된 애니메이션에서 화면상 캐릭터는 움직이는데 실제 월드 좌표는 제자리였습니다.

원인

이동량이 애니메이션의 로컬 좌표에만 적용되고 월드 행렬로 전달되지 않아, 연출 위치와 충돌 판정 위치가 어긋났습니다.

선택

애니메이션에서 이동을 빼고 코드로 옮기면 모션과 속도가 어긋나므로, 애니메이션의 이동량을 그대로 월드로 옮기는 쪽을 택했습니다.

구현

이동을 담당하는 본의 로컬 위치를 저장해 두고, 다음 갱신에서 그 차이를 월드 행렬에 전달한 뒤 해당 본의 위치를 원점으로 되돌렸습니다.

검증

동일 시작 좌표에서 대쉬를 반복해 종료 좌표와 충돌 판정 위치가 일치하는지 확인했습니다.

남은 한계

회전이 포함된 애니메이션에서는 회전량까지 함께 옮겨야 하는데, 이번 프로젝트에서는 이동량만 처리했습니다.

CASE 03

공격 궤적이 없어 타격감과 충돌 확인이 모두 어려웠던 문제

문제

공격 시 무기 궤적이 남지 않아 타격감이 약했고, 충돌이 활성화된 구간을 직관적으로 확인할 수 없었습니다.

원인

현재 프레임의 무기 위치만 렌더링되어 이동 궤적이 남지 않았고, 충돌 여부는 피격 애니메이션으로만 간접 확인할 수 있었습니다.

선택

파티클로 흉내 내면 무기 위치와 어긋나므로, 실제 무기 좌표를 추적해 궤적 메시를 만드는 방식을 택했습니다.

구현

충돌이 활성화된 프레임에서 검 손잡이와 검 끝 좌표로 버퍼를 구성하고, 간격이 넓으면 중간 지점을 추가해 스플라인 보간으로 메시를 생성했습니다.

검증

빠른 스윙 구간에서 궤적이 끊기지 않는지, 충돌 활성 구간과 궤적 표시 구간이 일치하는지 확인했습니다.

남은 한계

궤적 길이와 수명이 고정값이라 무기 종류별로 조정하려면 코드를 고쳐야 합니다.
